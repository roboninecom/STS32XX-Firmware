<a id="hardware-comparison-tests"></a>
# हार्डवेयर तुलना परीक्षण

STS सर्वो पर फ़ैक्टरी और कस्टम फ़र्मवेयर की तुलना करें। सुइट में विरासत प्रोटोकॉल, सेटिंग्स, गति, अंशांकन और सुरक्षा शामिल है। यह एक्सटेंशन प्रोटोकॉल v9 नियंत्रण का परीक्षण नहीं करता है. परीक्षण रिपॉजिटरी के [साझा ड्राइवर](../../host/servo-driver/README.md) का उपयोग करते हैं।

**सुरक्षित सर्वो और मुक्त शाफ्ट के साथ एक समर्पित बेंच का उपयोग करें।** कुछ परीक्षण लंबी या निरंतर चालें बनाते हैं और सहेजी गई सेटिंग्स या अंशांकन को प्रतिस्थापित करते हैं। पहले प्रत्येक सर्वो का बैकअप लें। मोटर की बिजली तुरंत काटने का उपाय रखें।

<a id="setup"></a>
## सेटअप

Node.js **20 या नया** इंस्टॉल करें, फिर रिपॉजिटरी रूट से चलाएं:

```sh
npm ci
npm run test:diff
npm run diff -- --list
```

ये आदेश ऑफ़लाइन चलते हैं. `--list` प्रत्येक परिदृश्य के चरण, गति वर्गीकरण और सटीक नाम को दर्शाता है। सभी कमांड विकल्पों के लिए `--help` का उपयोग करें।

केवल परीक्षण सर्वो कनेक्ट करें: कुछ मामले प्रसारण का उपयोग करते हैं। एडॉप्टर का उपयोग करके अन्य प्रोग्राम बंद करें और उपयुक्त मोटर आपूर्ति प्रदान करें। डिफ़ॉल्ट कनेक्शन हैं:

| सेटिंग | डिफ़ॉल्ट |
|---|---|
| फ़ैक्टरी सर्वो ID | `1` |
| कस्टम फ़र्मवेयर सर्वो ID | `2` |
| बॉड दर | `1000000` |

`--factory-id`, `--candidate-id` और `--baud` के साथ अलग-अलग मान सेट करें। आईडी अलग होनी चाहिए; आईडी **250 और 251** को अप्रयुक्त छोड़ दें क्योंकि परीक्षण उनका अस्थायी रूप से उपयोग करते हैं। टॉर्क ऑफ से शुरू करें, सेटिंग्स लॉक लिखी हुई हैं और कोई सक्रिय अलार्म नहीं है। गति की तुलना करते समय तुलनीय मोटरों, बिजली आपूर्ति और भार का उपयोग करें।

```sh
export SERVO_PORT=/dev/cu.usbmodemYOUR_ADAPTER
```

पोर्ट को अपने पोर्ट से बदलें. लिनक्स आमतौर पर `/dev/ttyUSB0` का उपयोग करता है; विंडोज़ पर, सीधे एक पोर्ट पास करें, जैसे `--port COM3`।

<a id="run-tests"></a>
## परीक्षण चलाएँ

संचार जाँच से प्रारंभ करें:

```sh
npm run diff -- --port "$SERVO_PORT" --case test_ping
```

डिफ़ॉल्ट समूह चलाएँ:

```sh
npm run diff -- --port "$SERVO_PORT" --stage safe
```

`safe` समूह PING की जांच करता है, रजिस्टर पढ़ता है और read-only रजिस्टर में लिखने की अस्वीकृति करता है। यह मोटरें नहीं चलाता है, लेकिन यह WRITE पैकेट भेजता है।

`--stage` वाला एक समूह चुनें, या `--case` वाला एक सटीक परिदृश्य चुनें:

```sh
npm run diff -- --port "$SERVO_PORT" \
  --case test_motion_write_order_gap_matrix --allow-motion
```

`--case` `--stage` को ओवरराइड करता है। फोकस्ड रन मौजूदा सर्वो सेटिंग्स का उपयोग करते हैं; वे पूर्ण सुइट का परीक्षण कॉन्फ़िगरेशन स्थापित नहीं करते हैं. यदि कोई मामला प्रारंभ नहीं हो पा रहा है तो उसकी रिपोर्ट की गई पूर्वापेक्षाओं की जाँच करें।

| अनुमति | अनुमति देता है |
|---|---|
| `--allow-motion` | ड्राइव को सक्षम करना या मोशन कमांड जारी करना |
| `--allow-persistence-write` | सहेजी गई सेटिंग्स लिखती हैं, अंशांकन और restore-defaults |
| `--allow-template-write` | सहेजे गए रीसेट टेम्पलेट को बदलना |
| `--allow-current-protection` | संचालित current-protection परीक्षण; गति अनुमति की भी आवश्यकता है |

पूर्ण सुइट के लिए सभी चार अनुमतियों और 1000000 की प्रारंभिक बॉड दर की आवश्यकता होती है:

```sh
npm run diff -- --port "$SERVO_PORT" --stage all \
  --allow-motion --allow-persistence-write \
  --allow-template-write --allow-current-protection
```

पहले non-passing मामले के बाद रुकने के लिए `--fail-fast` जोड़ें। अन्यथा, सामान्य विफलताओं के बाद भी स्वतंत्र मामले जारी रहते हैं। असफल पूर्वापेक्षाएँ, सफ़ाई विफलताएँ और खोया हुआ संचार आगे के परीक्षणों को रोक देता है।

<a id="settings-and-cleanup"></a>
## सेटिंग्स और सफ़ाई

**पूर्ण सुइट आपकी मूल सेटिंग्स को पुनर्स्थापित नहीं करता है।** यह एक सहेजे गए परीक्षण कॉन्फ़िगरेशन को स्थापित करता है और सर्वो के रीसेट टेम्पलेट को लोड करके समाप्त करता है। टेम्प्लेट परीक्षण उस टेम्प्लेट को सुइट सेटिंग्स से बदल देता है।

इन केंद्रित परीक्षणों का भी स्थायी प्रभाव होता है:

- `prerequisites` में restore-defaults और अंशांकन शामिल है। इसका ऑफसेट परीक्षण एक नया ऑफसेट बचाता है जो प्रदर्शित स्थिति को 2048 पर रखता है।
- `restore-defaults` सहेजे गए रीसेट टेम्पलेट (`0x06`) को लोड करता है, जो निर्माता की मूल सेटिंग्स से भिन्न हो सकता है।
- `template` रीसेट टेम्पलेट (`0x09`) को pre-test सक्रिय सेटिंग्स से बदल देता है। पुराने टेम्पलेट को इस सुइट द्वारा वापस पढ़ा या पुनर्स्थापित नहीं किया जा सकता है।

अन्य दृढ़ता के मामले उनके द्वारा बदली गई सेटिंग्स को पुनर्स्थापित करने का प्रयास करते हैं। दूसरे रन से पहले हमेशा सफ़ाई त्रुटियों का निरीक्षण करें। बैकअप कमांड और फ़ैक्टरी रिकवरी के लिए [सेटिंग्स बैकअप और रिकवरी गाइड](../flash/README.md#restore-factory-settings) देखें।

**Ctrl+C सफाई या सहेजी गई रिपोर्ट की गारंटी नहीं देता है।** रनर के पास कोई सुंदर रुकावट हैंडलर नहीं है। यदि गति तुरंत रुकनी चाहिए, तो मोटर की शक्ति काट दें; फिर जारी रखने से पहले संचार, सेटिंग्स और टॉर्क स्थिति को सत्यापित करें।

<a id="compare-against-a-saved-factory-run"></a>
## सहेजे गए फ़ैक्टरी रन से तुलना करें

समान मामलों, सुइट पुनरीक्षण, बॉड दर और तुलनीय बेंच स्थितियों का उपयोग करें:

```sh
npm run diff -- --port "$SERVO_PORT" --mode factory --case test_ping

npm run diff -- --port "$SERVO_PORT" --mode candidate --case test_ping \
  --reference tools/hw-diff-tests/results/FACTORY_TIMESTAMP/report.json
```

संदर्भ पथ को पहले रन की रिपोर्ट से बदलें। मूल फ़ैक्टरी ID को `--factory-id` में रखें; फ्लैशिंग के बाद एक ही भौतिक सर्वो का परीक्षण करते समय भी उम्मीदवार के पास एक अलग ID होना चाहिए। सुइट आपके लिए उस ID को नहीं बदलता है। Pair-only मामलों को single-device मोड में छोड़ दिया जाता है। `--reference` के बिना, single-device पास केवल उस परिदृश्य के दावों की जाँच करता है, फ़ैक्टरी तुल्यता की नहीं।

<a id="results"></a>
## परिणाम

रिपोर्टें `tools/hw-diff-tests/results/`, या `--results` के साथ आपूर्ति की गई निर्देशिका के अंतर्गत सहेजी जाती हैं। Git द्वारा परिणाम और लॉग को अनदेखा कर दिया जाता है।

प्रत्येक डिवाइस के अवलोकन, तुलना, प्रेषित पैकेट, प्राप्त प्रतिक्रियाओं और समय के लिए `report.json` खोलें। `fatal`, `cleanupError` और `closeError` के साथ-साथ मामले के परिणामों का निरीक्षण करें।

| नतीजा | मतलब |
|---|---|
| `passed` | दावे और कोई भी उपलब्ध तुलना पारित हो गई |
| `mismatch` | फ़ैक्टरी और उम्मीदवार की टिप्पणियाँ भिन्न थीं |
| `failed` | एक दावा, संचार या पुनर्प्राप्ति जांच विफल रही |
| `inconclusive` | फ़ैक्टरी ने तुलना के लिए आवश्यक प्रभाव उत्पन्न नहीं किया |
| `skipped` | केस नहीं चला |

निकास कोड **0** का अर्थ है कोई विफलता रिपोर्ट नहीं की गई; छूटे हुए मामले बने रह सकते हैं. **1** का अर्थ है argument/setup त्रुटि या हैंडल न किया गया अपवाद। **2** का अर्थ है कि रिपोर्ट में विफलता, बेमेल, अनिर्णायक परिणाम या cleanup/connection-close त्रुटि है।

समय में होस्ट शेड्यूलिंग, USB और क्रमिक विलंब शामिल हैं; यह फ़र्मवेयर निष्पादन समय का प्रत्यक्ष माप नहीं है। फर्मवेयर को गति अंतर का श्रेय देने से पहले रिपोर्ट को सुरक्षित रखें और एक केंद्रित मामले को पुन: पेश करें।
