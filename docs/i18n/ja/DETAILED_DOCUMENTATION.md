# 詳細なドキュメント

フラッシュ、テスト、リプレイ、重力補正については、**[クイック スタート](QUICKSTART.md)** ガイドから始めてください。個々のコマンド ガイドについては、[ツール](tools/README.md) を参照してください。

GD32F130-based STS3215 サーボ用ファームウェア。モーターを制御する 2 つの方法:

- **レガシー モード** は、位置、速度、モーター出力に標準の STS コマンドを使用します。デフォルトでは有効になっています。
- **拡張モード** では、スムーズな動き、調整可能な位置制御、動きと重力の補償が追加されます。接続されたコンピュータは設定と宛先を送信します。各サーボはその動きをローカルに計算します。

このドキュメントでは、機能がどのように動作するかを説明し、**拡張プロトコル v9.0** のコマンドとレジスタのリファレンスを提供します。拡張機能の設定は一時メモリに保存されるため、リセットまたは電源の再投入後に再度送信する必要があります。制御ソフトウェアはバージョン 9 をサポートする必要があります。古い拡張クライアントには互換性がありません。

<a id="legacy-mode"></a>
## レガシーモード

レガシー モードは、モーター電力、動作モード、位置および速度コマンド、ステータス読み取りなどの標準 STS レジスタ インターフェイスをサポートします。既存の STS ソフトウェアは、拡張機能を有効にしなくてもレジスタ **0–86** を使用できます。

従来の位置モードでは、新しい位置コマンドを使用せずにモーター出力を有効にすると、保存された制限の範囲外であっても測定された位置が保持されます。古いターゲットを再生したり、シャフトを限界に近い位置まで動かしたりすることはありません。新しい位置コマンドは、保存された制限に制限されたままになります。

拡張機能は独自のモーションとコントロール設定を使用します。スケールが異なるため、2 つのモード間でゲイン値を直接コピーしないでください。標準コマンドのサポートは、すべてのサーボ モデルで同一の物理的動作を保証するものではありません。

<a id="how-extension-mode-works"></a>
## 拡張モードの仕組み

[録画された概要を YouTube でご覧ください](https://youtu.be/AsxFs24vXQs) | [MP4](../../../assets/readme/videos/overview.mp4)

**ホスト** は、サーボに接続されているコンピューターまたはコントローラーです。 **ターゲット**: 目的地と制限速度を送信します。加速と補償の設定は、モーター電力を有効にする前に構成されます。各サーボは次のようになります。

1. 目的地に向かってスムーズな移動を計画します。
2. 位置を測定し、速度を推定します。
3. 計画した動きに追従するようにモーター出力を調整します。
4. 移動終了時に目的地を保持します。

ある時点での計画された位置と速度は **基準** と呼ばれます。コントローラは測定された動きと比較するため、基準位置と実際の位置が異なる場合があります。

このドキュメント全体で使用されるいくつかの用語:

| 期間 | 意味 |
| --- | --- |
| エンコーダ数 | 位置測定ユニットと、公称 1 回転あたり 4096 カウント |
| 努力 | 符号付き motor-output コマンド: その符号は方向を設定し、そのサイズは出力強度を設定します |
| ゲイン | コントローラーの反応の強さを決定する設定 |
| フィードフォワード | 位置や速度のエラーを待つのではなく、予想される需要から計算される追加のモーター出力 |
| フィードバック | サーボから返される測定値とステータス |
| 登録する | 数字で識別される設定または読み取り値 |
| セッション | 拡張制御の 1 つの期間。ホストによって提供される番号によって識別されます。 |

努力は、モーターへの電気出力を制御するために使用される単位である PWM 単位で表されます。この拡張により、どちらの方向でも最大 **1000** までの出力制限が可能になります。これらの値は、トルクや電流を直接測定したものではありません。

<a id="s-curve-motion"></a>
## S-curveモーション

[![s-curveモーション](../../../assets/readme/illustrations/s-curve.png)](https://youtu.be/92mDt4rbobY)の概念図

[YouTubeで見る](https://youtu.be/92mDt4rbobY) | [MP4](../../../assets/readme/videos/s-curve.mp4)

加速とブレーキをより緩やかにします。曲線は時間の経過に伴う加速を示しています。概念図であり、測定されたハードウェア データではありません。

S-curve は加速度を徐々に増加および減少させます。突然フル加速やブレーキをかけるのではなく、サーボは動作の各部分に緩やかに出入りします。これにより、機械的な衝撃や振動を軽減できます。

休息から休息への完全な動きには次の段階があります。

| ステージ | 何が起こるか |
| --- | --- |
| 1 | 徐々に加速が増していく |
| 2 | サーボは一定の速度で加速します |
| 3 | 加速度は徐々にゼロに減少します |
| 4 | サーボは一定の速度で動きます |
| 5 | 徐々にブレーキが強くなる |
| 6 | サーボは一定の速度でブレーキをかけます |
| 7 | サーボ停止に伴い徐々にブレーキが弱くなる |

要求された速度または加速度に達するのに十分な距離がない場合、短い移動はステージをスキップします。加速時と減速時に同じ加速制限が適用されます。

`ramp_time_ms` 設定は、加速がゼロから限界まで上昇するまでにかかる時間を制御します。ランプが長いほど変化は緩やかになりますが、一般に加速または停止するためにより多くの時間と距離が必要になります。

**ジャーク**は、加速度が変化する速度を意味します。このプランナーはジャークを制限し、加速度が滑らかに変化します。ジャーク自体は、ステージ間で突然変化する可能性があります。そのおおよその大きさは次のとおりです。

```text
jerk = 1000 × acceleration / ramp_time_ms    [counts/s³]
```

<a id="changing-a-destination-during-movement"></a>
### 移動中の目的地変更

新しいターゲットは、その位置、速度、加速度を維持しながら、現在計画されている動作を継続します。同じ宛先を再度送信しても、移動は再開されません。移動中は要求された速度制限を維持してください。計画された動きが停止すると、次の動きに向けて変更される可能性があります。加速とランプ時間は構成に属しており、変更するにはモーターの電源をオフにし、セッションを解除する必要があります。

保存された Legacy の位置制限の外にある目標は、**最も近い境界に制限されます**。要求速度も設定された上限に制限されます。サーボは各移動で設定された加速度を使用します。速度がゼロの場合、または設定された加速度がゼロの場合は無効です。

計画された動き全体が位置制限内に収まらなければなりません。したがって、サーボがその範囲内で停止するには速すぎる限界にすでに近づいている場合は、目的地自体が許可されている場合でも、新しいターゲットは拒否される可能性があります。

到着すると、モーターの電源がオンになった状態で、サーボが自動的に目的地を保持します。測定された位置には、摩擦、負荷、出力制限、チューニングなどにより多少の誤差が生じる場合があります。押し続けると位置誤差が修正されます。モーター出力が固定値で固定されることはありません。

各サーボは独自の動きを計画します。複数のターゲットを一緒に送信しても、すべてのサーボが同時に到着することは保証されません。

<a id="shared-position-limits"></a>
### 共有ポジション制限

レガシー制御と拡張制御は同じ position-limit レジスタを使用します。**9–10** には最小値が含まれ、**11–12** には最大値が含まれます。それぞれは、サーボの設定された方向と位置の補正を含む、補正されたエンコーダー カウントの符号なし 16 ビット値です。個別のExtension position-limit 設定はありません。

キャリブレーションにより、エンコーダー カウントが物理的な位置に割り当てられます。 [キャリブレーション ツール](tools/settings/README.md#choose-the-reference-pose) は、キャプチャされた基準姿勢を読み取り 2048 にし、移動限界を測定します。そのカウントは自動的に zero-degree ジョイント角度になるわけではなく、測定された移動中点はキャプチャされた基準に置き換わることはありません。重力モデルとビジュアライゼーションには、一致する count-to-angle マッピングが必要です。

ファームウェアは制御開始時にこれらのレジスタを読み取ります。位置制限が有効な場合、最小値は最大値未満、最大値は 32767 以下で、測定位置がその範囲内にある必要があります。条件を満たさない場合は起動に失敗し、モーターは動きません。プランナーは制動を含む動作全体を、読み取った範囲内に保ちます。

**最小値と最大値が等しいと移動制限が無効になり**、従来の動作と一致します。拡張コマンドは、サポートされている位置範囲 −32767 から 32767 カウント内に留まります。

いずれかの制限への書き込みが受け入れられると、アクティブな拡張セッションが終了し、RAM でのみ適用される書き込みを含め、モーターの電源がオフになります。変更された値を使用するために新しいセッションを準備します。通常のレガシー設定の永続性は引き続き適用されます。

<a id="pid-controller"></a>
## PIDコントローラー

[![pid 制御の概念図](../../../assets/readme/illustrations/pid-tuning.png)](https://youtu.be/TEpvaAMlfrg)

[YouTubeで見る](https://youtu.be/TEpvaAMlfrg) | [MP4](../../../assets/readme/videos/pid-tuning.mp4)

サーボによる位置誤差の補正方法を調整します。灰色の曲線は振動を示しています。白い曲線は、より減衰した応答を示しています。破線がターゲットです。概念図であり、測定されたハードウェア データではありません。

PID コントローラーは、計画された動きに従うようにモーターの出力を調整します。その 3 つの設定には異なる役割があります。

| 設定 | 何をするのか | 主なトレードオフ |
| --- | --- | --- |
| **P — 位置補正** | モーターを計画された位置に向かって引っ張ります。エラーが大きくなると、より多くの修正が行われます | P を高くすると誤差は減少しますが、発振が発生する可能性もあります |
| **I — 累積補正** | エラーが続く場合は追加の修正を蓄積します | 永続的なエラーを減らすことができますが、オーバーシュートや整定時間が長くなる可能性があります |
| **D — 速度補正** | 計画速度と測定速度の差に応答します。保持中に動きに抵抗する | ダンピングを改善できますが、ノイズの多い速度読み取り値に対する過剰な応答により、出力が不均一になる可能性があります。 |

計算は次のとおりです。

```text
position error = planned position − measured position
speed error = planned speed − filtered measured speed

motor output = Kp × position error
             + Kd × speed error
             + accumulated I correction
             + gravity compensation
             + velocity feedforward
```

結果は、設定された最大出力に制限されます。モーターを保護すると、さらに減少する可能性があります。フィードバックは要求された出力と適用された出力の両方を報告するため、ホストはモーターがいつ制限されているかを確認できます。

測定された速度は、最近の位置読み取り値と調整可能なフィルターを使用して平滑化されます。 `velocity_filter_q8` 設定を大きくすると、変化に対する反応が速くなりますが、除去される測定ノイズは少なくなります。

<a id="preventing-excessive-accumulated-correction"></a>
### 過剰な累積補正の防止

I の貢献には独自の制限があります。また、コントローラーは、モーター出力がすでに制限されている方向にコントローラーが構築され続けるのを防ぎます。これは一般に **anti-windup** と呼ばれます。モーターがその制限から回復するのを助けるために、さらに減少する可能性があります。 `Ki` をゼロに設定すると、I 補正が無効になり、クリアされます。

サーボが少なくとも 50 ミリ秒間ほぼ静止しており、位置誤差が 1 エンコーダー カウント以内にある場合、I の累積は停止します。 P、D、および両方の形式のフィードフォワードはアクティブのままです。モーター出力をオフにすると、I 補正は解除されます。

<a id="velocity-feedforward"></a>
## 速度フィードフォワード

[![速度フィードフォワードの概念図](../../../assets/readme/illustrations/velocity-feedforward.png)](https://youtu.be/osGGs-nhk9I)

[YouTubeで見る](https://youtu.be/osGGs-nhk9I) | [MP4](../../../assets/readme/videos/velocity-feedforward.mp4)

サーボ内部で計算された計画速度に基づいてモーター出力を加算します。どちらの曲線も時間の経過とともに左から右に進みます。概念図であり、測定されたハードウェア データではありません。

速度フィードフォワードは、追跡エラーが発生する前に、移動に必要とされる出力の一部を供給します。これは、計画された速度から**サーボ内部**で計算されます。

```text
velocity feedforward = velocity gain × planned speed
```

各方向に 1 つのゲインがあり、結果の出力には制限があります。どちらのゲインも負ではありません。移動方向によって出力符号が決まります。その出力制限はメインの motor-output 制限を超えてはなりません。

サーボは自身の計画速度を知っているため、補正は加速と制動に自動的に追従し、計画された動作が停止するとゼロになります。ホストはその設定のみを提供します。連続した velocity-feedforward 値を送信する必要はありません。

この機能は、モーターの電源がオフでセッションが解除されている間に、`0xA0` の他の設定と一緒に構成します。無効にするには、両方のゲインとその出力制限をゼロに設定します。

<a id="gravity-compensation"></a>
## 重力補正

[![重力補正の概念図](../../../assets/readme/illustrations/gravity-compensation.png)](https://youtu.be/25sc41PTDIA)

[YouTubeで見る](https://youtu.be/25sc41PTDIA) | [MP4](../../../assets/readme/videos/gravity-compensation.mp4)

ホストが寄与を計算し、サーボがそれを適用します。下向きの矢印は重量を表します。上向きの矢印はサポートを表します。概念図であり、測定されたハードウェア データではありません。

重力補償は、アームの重量とその荷重を支えるのに必要な出力を提供します。これは、モーターが静止しているとき、つまり速度フィードフォワードがゼロのときでも役立ちます。

**ホストは重力補正**を計算し、符号付きの出力値を各サーボに送信します。計算には、ジョイント角度、アーム寸法、リンク重量、ペイロードを使用できます。ホストは推定負荷をサーボの出力単位に変換する必要があります。ファームウェアには腕のモデルは含まれていません。

方向が重要です。エンコーダー数の増加に伴い、正の拡張出力が続きます。 arm の joint-angle 規則は逆方向に実行される可能性があるため、ホストの変換はそれを考慮する必要があります。

各重力更新には、必要な出力値が含まれます。 **スルー レート** (補正がどのくらい早く変化するかを 1 秒あたりの出力単位で表す) は、主要な設定の一部であり、セッション全体を通じて固定されます。

サーボは要求された値に向かって補償を徐々に変更し、それをコントローラーの出力に追加します。すべての寄与は合わせて、設定された出力制限とモーター保護の影響を受け続けます。

**重力更新の受信が停止した場合、サーボは設定されたスルー レートで最後に要求された補正に向けて続行し、その値を維持します。** 有効期限タイマーはありません。ホストは、腕のポーズや負荷が変化したときに補正を更新する必要があります。 torque-enable レジスタ **40** をゼロに設定すると、補償がクリアされ、モーター出力がオフになります。

<a id="starting-and-stopping-extension-mode"></a>
## 拡張モードの開始と停止

次のシーケンスでは、後で説明するレジスタ番号とコマンドを使用します。選択するとセッションが準備されます。モーターパワーを有効にすると制御が開始されます。

1. 接続されているサーボ ID を見つけて、各サーボの機能を読み取ります。 `ARMC` とバージョン `9.0` を確認してください。リセットまたはファームウェアの変更後にこのチェックを繰り返します。
2. レガシー torque-enable レジスタ **40** を `0` に設定して、モーターの電源をオフにします。既存のセッションを終了し、永続的なレガシー設定を適用します。
3. 速度フィードフォワード設定や重力スルーレートを含む完全な構成 (`0xA0`) を書き込んで読み戻します。
4. `mode=1` とゼロ以外の新しいセッション番号を `0xB8` に書き込みます (合計 3 バイト)。これにより拡張モードが選択され、次の開始の準備が整います。電源はオフのままです。
5. レジスタ **40** を `1` に設定します。ファームウェアはセンサー、保護ステータス、構成、保存された位置制限をチェックし、測定された位置を初期保持ターゲットとしてキャプチャします。コマンドカウンター、I補正、重力補正はゼロからスタートします。 `0xC1` を読み取って、正しいセッション、現在使用可能な測定値、モータードライブが有効になり、出力の準備が完了するまで待ちます。
6. ターゲットと重力の最新情報を送信します。フィードバックを読んで、どのコマンドが受け入れられたか、サーボがそれらのコマンドにどれだけ忠実に従っているかを確認します。
7. サーボは最後の移動を終了し、新しいターゲットが与えられるまで目的地を保持します。モーターの電源をオフにしてセッションを終了するには、レジスタ **40** を `0` に設定します。レガシーモードに戻るには、電源をオフにしたまま、`mode=0, session=0` から `0xB8` に書き込みます。

起動に失敗した場合、レジスタ**40**は`0`に戻ります。通常の書き込み確認だけでは起動の成功を確認できません。レジスタのリードバックとフィードバックを確認してください。開始を試行するたびに、準備されたセッションが消費されます。始動、torque-off、または保護シャットダウンの失敗後、原因を修正し、トルクを再度有効にする前に、新しいセッション番号を`0xB8`に書き込みます。制御の実行中にトルクの有効化を繰り返すと、そのターゲット、補償、およびコマンドのカウンターが保存されます。

動力付きモーターを動かしたり調整したりするコマンドには、ハードウェアが準備されていること、障害が報告されていないこと、センサーの読み取り値が **2 ミリ秒** 以内であることが必要です。コントローラーは通常 **1 ミリ秒** ごとに更新し、最大 2 ミリ秒の間隔を受け入れます。ギャップが長いとモーター出力が無効になります。

拡張機能を使用している間は、動作モード レジスタ **33** またはモーション レジスタ **41–47** へのレガシー書き込みを避けてください。これらの書き込みにより、モーターの電源がオフになり、拡張モードが終了します。永続的な設定を保存すると、拡張機能の制御も終了します。レジスタ **40** を `0` に設定すると、拡張モードが選択されたままになり、別のセッション設定の準備が整います。

<a id="if-host-commands-stop-arriving"></a>
### ホストコマンドが到着しなくなった場合

サーボは最後に受け入れられた移動を終了し、その目的地を保持し続けます。重力補正は、最後に要求された値に向かって継続し、そこに留まります。セッションをアクティブに保つためにメッセージを繰り返す必要はなく、ホスト通信が失われてもターゲットが変更されたり、モーターの電源がオフになったりすることはありません。

サーボの移動先を変更するには、別のターゲットを送信します。モーターを解放するには、トルクイネーブルをゼロに設定します。センサーの鮮度チェック、モーター保護、ファームウェア ウォッチドッグは、移動中や保持中にもアクティブなままになります。

<a id="extension-protocol"></a>
## 拡張プロトコル

このセクションでは、ホストとサーボ間で交換される正確なメッセージについて説明します。これは、独自のソフトウェアを接続する読者を対象としています。

<a id="message-format-and-number-encoding"></a>
### メッセージ形式と数値エンコーディング

各メッセージはパケットです。宛先、コマンド、データ、および送信エラーの検出に使用されるチェックサムを含む一連のバイトです。拡張コマンドは、標準の STS パケット形式を使用します。

```text
Request:  FF FF ID LENGTH INSTRUCTION PARAMETERS... CHECKSUM
Response: FF FF ID LENGTH LEGACY_ERROR EXT_STATUS DATA... CHECKSUM
```

- `LENGTH = parameter_bytes + 2` をリクエストします。
- 応答 `LENGTH = data_bytes + 3`;拡張ステータスは、通常のレガシー エラー バイトとは別に、最初の応答パラメータを占めます。
- `CHECKSUM = ~(ID + LENGTH + instruction_or_error + all_parameter_bytes) & 0xFF`。応答合計には、`EXT_STATUS` と任意のデータが含まれます。
- 数バイトを占めるフィールドは、最下位バイトを最初に送信します (**little-endian**)。たとえば、数値 256 は 2 バイトの `00 01` として送信されます。
- `u8`、`u16`、`u32` は、1、2、4 バイトを占める非負の整数です。 `i16` と `i32` は 2 と 4 バイトを占有し、負の数を表すこともできます。符号付き拡張値には **2 の補数** が使用されます。たとえば、−1 は、`i16` フィールドでは `FF FF` になります。これは、符号付き値の従来のエンコードとは異なります。
- **Q8** は、送信前に値が 256 で乗算され、分数が整数として表現されることを意味します。 256で割って読んでください。たとえば、位置1000 カウントは256000 として送信され、ゲイン4.5 は1152 として送信されます。
- 位置はエンコーダーカウントで表され、速度はcounts/sで表されます。ホストは、方向やゼロ位置の変更を含む、ジョイント角度へのあらゆる変換を処理します。
- **ユニキャスト** は、1 つのサーボに宛てられたメッセージを意味します。 **ブロードキャスト** は ID `0xFE` を使用し、すべてのサーボに到達します。ブロードキャスト拡張コマンドは応答を生成しません。

例: サーボ ID 1 から 8 バイト機能ブロックを読み取ります。

```text
FF FF 01 04 90 90 08 D2
```

**セレクター** は、構成やフィードバックなどの完全なレジスタ ブロックを識別します。Extension READ/WRITE と以下に示す正確なブロック サイズを使用してアクセスします。ブロックの一部のみの読み取りまたは書き込みはサポートされておらず、従来の READ/WRITE コマンドはこれらのブロックにアクセスできません。

<a id="instructions"></a>
### 指示

以下のパラメータ サイズには、パケット ヘッダーとチェックサムは含まれません。応答では、`EXT_STATUS` は、サーボの通常のエラーバイトである `LEGACY_ERROR` とは別に、拡張コマンドが成功したかどうかを報告します。読み取りが成功すると、要求されたデータが `EXT_STATUS` の後に追加されます。書き込み、その他のコマンド、および失敗した読み取りには追加のデータはありません。

| 指示 | 名前 | パラメータ | ブロードキャスト |
| --- | --- | --- | --- |
| `0x90` | READ | `selector:u8, count:u8` | 有用な応答はありません |
| `0x91` | WRITE | `selector:u8, block...` | 受け入れられません |
| `0x99` | GRAVITY | 6 バイト、以下 | 受け入れられません |
| `0x9A` | TARGETS | `session:u16` + 1–6 9 バイトのエントリ | 承認されました |

命令番号`0x92`、`0x93`、`0x94`、`0x95`、`0x96`、`0x97`、`0x98`、セレクタ`0xA1`、`0xA3`、`0xB0`、`0xBA`、`0xE0`、および `0xF0` は予約されているため、使用しないでください。

| 拡張ステータス | 意味 |
| --- | --- |
| `0` | OK |
| `1` | 無効な長さ、セレクター、またはフィールド値です |
| `2` | 現在の状態ではコマンドを受け付けられません |
| `3` | 予約済み |
| `4` | 予約済み |
| `5` | サポートされていない命令 |

セッションの不一致は状態エラーを返します。従来のエラー バイトと拡張ステータスの両方を検査します。

<a id="sessions-and-sequence-numbers"></a>
### セッションとシーケンス番号

ホストは各セッションに 1 から 65535 までの番号を割り当て、制御コマンドに含めます。これにより、サーボはコマンドが現在のセッションに属していることを確認できます。起動ごとに新しい番号を選択します。セットアップ番号は永続的に保存されるわけではありません。

**シーケンス番号**は受け入れられたコマンドを順番にカウントし、ホストとサーボが欠落コマンド、繰り返しコマンド、またはout-of-orderコマンドを識別できるようにします。

TARGETS には per-servo モーション シーケンス カウンターがあります。 GRAVITYには独立したカウンターがあります。トルクイネーブルが制御を開始すると、両方ともゼロから始まります。通常は最初に **1** を送信します。数字は 65535 まで増加し、その後セッションを終了せずに **0** まで戻ります。ギャップは許容されます。10 の後は、11 が失われたか拒否された場合でも、サーボは 12 を受け入れることができます。現在のコマンドを変更せずに、同じまたは古い番号は拒否されます。

正確に比較するには、`distance = (incoming − accepted) & 0xFFFF` を計算します。コマンドは `1 ≤ distance ≤ 32767` の場合にのみ新しいものになります。正確に 32768 のジャンプは曖昧で拒否されます。最後に受け入れられたコマンドからのギャップを 32768 未満に保ちます。コマンド履歴が不確実な場合は、トルクをオフにして、新しいセッション ID を準備して、トルクを再度有効にします。以前のセッションまたはカウンタ サイクルからキューに入れられたパケットを再利用しないでください。

受け入れには、有効なフィールド、現在のセンサー読み取り値、および実行可能な動作が必要です。拒否されたコマンドはカウンタを進めません。これらのコマンドは絶対ターゲットを置き換えます。これらはウェイポイントキューではありません。すべてのウェイポイントを訪問するには、各到着を待ってから次の目的地に送信します。

グループターゲットを送信するときは、各サーボのフィードバックを読んで、受け入れられたシーケンスを確認します。各サーボは、そのターゲットを受け入れることができるかどうかを個別に決定します。他の人が動き始める間、1人はそれを拒否するかもしれません。

<a id="targets--0x9a"></a>
### TARGETS — `0x9A`

最初の 2 つのパラメータ バイトには共有セッションが含まれます。以下の各エントリはこのレイアウトになっています。オフセットはそのエントリの先頭からの相対値です。

| オフセット | 種類 | フィールド |
| --- | --- | --- |
| 0 | `u8` | サーボ ID、1–253 |
| 1 | `u16` | このサーボの新しいモーション シーケンス |
| 3 | `i32` | 目的地位置、Q8 カウント |
| 7 | `u16` | 最大速度、counts/s、ゼロ以外 |

パラメータの長さは `2 + 9 × entry_count`、最大 56 バイトです。 ID は一意である必要があります。各サーボは、独自のエントリを処理する前に、**すべて** エントリの形式と必須フィールドをチェックします。記載されていないサーボは何も動作しません。リストされたサーボは、そのセッション、シーケンス、準備状況、および動きが制限内に収まるかどうかをチェックします。受け入れられたターゲットはすぐに開始され、置き換えられるか武装解除されるまでアクティブのままになります。 S-curve モーションで説明されているように、値は設定された制限に制限されます。

<a id="gravity--0x99"></a>
### GRAVITY — `0x99`

| オフセット | 種類 | フィールド/制約 |
| --- | --- | --- |
| 0 | `u16` | 現在のセッション |
| 2 | `u16` | 新しい重力シーケンス |
| 4 | `i16` | 望ましい重力の作用。大きさ ≤ 設定された出力制限 |

パラメータの長さは正確に 6 バイトです。モーターの電源がオンで、ハードウェアの準備ができており、障害が報告されておらず、最近のセンサーの読み取り値を備えた武装セッションが必要です。モーションシーケンスは進みません。要求された値は、交換または解除されるまでアクティブのままです。

<a id="extension-registers"></a>
## 拡張レジスタ

**オフセット**はフィールドの開始バイトであり、そのブロック内でゼロからカウントされます。以下のオフセットは 10 進数です。セレクターは 16 進表記 (`0x...`) を使用します。すべての書き込みには命令 `0x91` が使用されます。読み取りでは、正確なバイト数で `0x90` を使用します。

| セレクター | ブロック | アクセス | バイト |
| --- | --- | --- | --- |
| `0x90` | 能力 | 読む | 8 |
| `0xA0` | 構成 | Read/write | 24 |
| `0xB8` | コントローラーの選択とセッションのセットアップ | 書く | 3 |
| `0xC1` | 運用上のフィードバック | 読む | 32 |
| `0xC2` | チューニングフィードバック | 読む | 54 |

<a id="capabilities--0x90"></a>
### 能力 — `0x90`

| オフセット | 種類 | 価値・意味 |
| --- | --- | --- |
| 0–3 | 4バイト | ASCII `ARMC` |
| 4 | `u8` | メジャーバージョン: 9 |
| 5 | `u8` | マイナーバージョン: 0 |
| 6 | `u8` | 予約済み: 0 |
| 7 | `u8` | 通常のコントローラー更新間隔: 1 ミリ秒 |

プロトコルのバージョンは、使用可能なブロックとその正確な長さを定義します。以下に説明するように、選択とセッションのセットアップは 1 つの write-only ブロックを共有します。

<a id="configuration--0xa0"></a>
### 構成 — `0xA0`

| オフセット | 種類 | フィールド | 単位/有効範囲 |
| --- | --- | --- | --- |
| 0 | `u16` | `kp_q8` | ゲイン × 256; 0–65535 |
| 2 | `u16` | `kd_q8` | ゲイン × 256; 0–65535 |
| 4 | `u16` | `ki_q8` | ゲイン × 256; 0–65535 |
| 6 | `u16` | `integral_limit` | 努力; 0–`effort_limit` |
| 8 | `u16` | `effort_limit` | 努力; 1–1000 |
| 10 | `u16` | `velocity_limit` | Counts/s; 1–65535 |
| 12 | `u16` | `acceleration_limit` | Counts/s²; 1–30000 |
| 14 | `u8` | `velocity_filter_q8` | Speed-filter 応答; 1–255、高いほど応答が速くなります |
| 15 | `u8` | `ramp_time_ms` | 加速ランプ; 1–255ミリ秒 |
| 16 | `u16` | `velocity_ff.positive_gain_q8` | 出力/(count/s) × 256; 0–65535 |
| 18 | `u16` | `velocity_ff.negative_gain_q8` | 出力/(count/s) × 256; 0–65535 |
| 20 | `u16` | `velocity_ff.effort_limit` | 努力; 0 – メイン `effort_limit` |

ゲインは、希望の値に256を乗算して送信されます。それらの単位は、P の場合は output/count、D の場合は出力/(count/s)、I の場合は出力/(カウント・秒) です。たとえば、P = 4.5 の場合、エラーのカウントごとに 4.5 の出力単位が生成され、1152 として送信されます。

サーボには **1 つのアクティブな構成**があります。これを書き込むには、モーターの電源をオフにし、セッションを解除する必要があります。書き込みごとに、フィードフォワード設定を含む構成全体が置き換えられます。無効な設定では、何も変更せずに書き込み全体が拒否されます。 `0xA0` を読んで、受け入れられた設定を確認します。

Velocity-feedforward のゲインは負ではありません。フィードフォワード出力制限をゼロにするには、両方のゲインがゼロである必要があります。同じフィードフォワード出力制限が両方向に適用され、メイン出力制限を超えてはなりません。

リセット後、モーター電源を有効にする前にサーボを設定します。保存された設定と代替調整値をホスト上に保持します。アームを支え、モーターの電源をオフにして、実行間でゲインを変更します。

<a id="selection-and-session-setup--0xb8"></a>
### 選択とセッションのセットアップ — `0xB8`

| オフセット | 種類 | 意味 |
| --- | --- | --- |
| 0 | `u8` | モード: `0` レガシー、`1` 拡張 |
| 1 | `u16` | セッション: レガシーの場合は `0`、拡張の場合は `1–65535` |

正確なペイロード長は **3 バイト**で、セッションは little-endian の順序になります。たとえば、セッション `0x1234` の拡張モードは `01 34 12` です。レガシーモードは`00 00 00`です。無効な組み合わせは、状態を変更せずに書き込み全体を拒否します。どちらのモードでもモーターの電源をオフにし、以前のセッション設定を置き換える必要があります。選択だけでは制御が開始されず、保持位置も取得されません。

レガシー torque-enable レジスタ **40** は、`1` に書き込まれると、準備された拡張セッションを開始します。それには、利用可能なモーター出力、有効な構成、読み取り値が 2 ミリ秒以内で初期化されたセンサー、シャットダウンを必要とする障害がないこと、および使用可能な保存された従来の位置制限が必要です。有効な場合、測定された位置はこれらの制限内にある必要があります。これらのチェックは有効化時に行われるため、セットアップと有効化の間の移動や障害が考慮されます。

Torque-off は、実行制御と未使用のセットアップの両方をキャンセルします。センサーの故障、保護のシャットダウン、position-limit または encoder-offset の変更、キャリブレーション、永続的な設定の保存も、セッションのセットアップを無効にします。フィードバックを読んで、実際に制御が開始されたかどうかを確認します。個別の ARM コマンドはありません。以前の `0xBA` セレクターと以前の one-byte 選択ペイロードは拒否されます。

| 14 | アームコントローラーを選択しました |
| 15 | 予約済み: ゼロ |

各フラグは 1 ビットです。ビット 0 の値は 1、ビット 1 の値は 2、ビット 2 の値は 4 などです。複数のフラグを一度に設定できます。ビット 12 がクリアされているアクティブなコントローラーは、宛先を保持しています。モーション ビットがクリアされているだけでは、モーターに電力が供給されていること、または準備が整っていることを意味するものではありません。

フィードバックは記録された測定値を説明します。ホストがサーボを読み取る前にサーボの状態が変化した場合、一部のフィールドに以前の状態が記述される場合があります。ビット 0 は、測定が 2 ミリ秒経過したとき、コントローラーが選択されていない、作動状態、運転中、または準備完了状態になっていない場合、またはコントローラーの session/sequence 番号が一致しなくなったときにクリアされます。ビット 0、年齢、セッション、および受け入れられたシーケンスを一緒にチェックします。

位置とヘルスの測定値は、レガシー モードおよびモーター電源オフでも利用できます。使用できない制御フィールドはゼロです。サンプル シーケンスは、ホストが測定値を読み取るたびではなく、測定値が取得されるときに進みます。同じミリ秒のタイムスタンプを共有するサンプルを区別します。予期しない大きな温度変化は、ここに表示される前に複数の測定値にわたってチェックされます。以下の保護制限を参照してください。

<a id="tuning-feedback--0xc2"></a>
### チューニングフィードバック — `0xC2`

バイト 0–31 のレイアウトは正確に `0xC1` です。残りのバイトは次のとおりです。

| オフセット | 種類 | フィールド / ユニット |
| --- | --- | --- |
| 32 | `i32` | 基準位置、Q8 カウント |
| 36 | `i32` | 基準速度、Q8 counts/s |
| 40 | `i16` | 設定された制限の後、モーター保護の前に要求された出力 |
| 42 | `i16` | P貢献、努力 |
| 44 | `i16` | D 貢献、努力 |
| 46 | `i16` | 全面的な貢献、努力 |
| 48 | `i16` | 現在適用されている重力補正、努力 |
| 50 | `i16` | ローカル速度フィードフォワード、エフォート |
| 52 | `u16` | 累積された追加のコントローラー遅延 (ミリ秒)。最大65535 |

コントローラーの更新に通常の 1 ミリ秒 (`elapsed_ms − 1`) を超える時間がかかる場合は、遅延カウンターにより追加時間が追加されます。失われたメッセージはカウントされません。報告される P および D の寄与は ±32767 に制限されているため、表示された値を加算しても完全な内部計算が再現されない可能性があります。

サーボは、要求された場合にのみフィードバックを送信します。通常のモニタリングには `0xC1` を使用し、チューニングに追加の値が必要な場合には `0xC2` を使用します。 `0xC2` を読み取ると、すでに `0xC1` がすべて含まれているため、両方を読み取ると不必要にトラフィックが増加します。個別の読み取りでは、異なる瞬間を参照できます。タイムスタンプとサンプル番号を比較します。

<a id="build-and-verification"></a>
## 構築と検証

ファームウェアのソース、テスト、ビルド ルールは [`firmware/`](firmware/README.md) にあります。 [ツールチェーン](firmware/README.md#build-and-verify) をインストールした後、次を実行します。

```sh
make
make verify
```

ビルド出力は無視される `build/` になります。検証はオフラインで行われ、ハードウェアはフラッシュされません。ホスト、flashing-tool、およびビューアのテストについては、[プロジェクト チェック](tools/README.md#offline-checks)を参照してください。公開されたファームウェア リリースをインストールするには、[フラッシュおよび回復ツール](tools/flash/README.md) を使用します。

<a id="current-limits"></a>
## 電流制限

[![ギアボックスのバックラッシュとフレームのフレックス](../../../assets/readme/posters/mechanical-limits.jpg)](https://youtu.be/53l7at5aE6k)

[YouTubeで見る](https://youtu.be/53l7at5aE6k) | [MP4](../../../assets/readme/videos/mechanical-limits.mp4)

拡張フィードバックを通じて報告された温度は、孤立したジャンプを抑制するためにチェックされますが、モーターの温度保護では依然として生のセンサー読み取り値が使用されます。これは、たとえそれが拡張機能のフィードバックから除外されたとしても、短時間の不正な読み取りが保護に影響を与える可能性があることを意味します。

ゲイン、制限、補償は実際のメカニズムに合わせて調整する必要があります。ソフトウェアテストだけでは、アームが負荷の下でどのように動作するかを確立することはできません。測定された位置、速度、および適用された出力を確認して、精度、整定、およびモーターが出力限界に達しているかどうかを評価します。
